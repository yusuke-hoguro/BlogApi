## 理解の記録

### 説明できるようになったこと

- Terraform管理対象と既存AWSリソースを明確に区別する必要性。
- 初回学習で対象範囲をEC2とSecurity Groupに限定する理由。
- AMIのOS・CPUを決めることと、具体的なAMI IDの取得方法を決めることの違い。
- `t3.micro`を学習用途に採用し、Variableで変更可能にする理由。
- Security Groupでは必要なポートだけを許可すること。
- SSHの`0.0.0.0/0`公開を短時間の学習・デモに限定する理由。
- 設計書で学習用構成と実務推奨構成を分けて説明する意義。
- Codexへ実装を依頼する前に未決定事項を明示する必要性。

### 重要な設計判断

| 判断 | 採用理由 | 前提・制約 | 参照先 |
| --- | --- | --- | --- |
| Terraform管理対象をEC2 1台とSecurity Group 1個に限定する | TerraformとEC2の基本理解を優先するため | ネットワークは既存リソースを利用 | 設計書3〜5章 |
| VPC、Subnet、Internet Gateway、Route Tableを管理対象外にする | 学習範囲を広げすぎないため | 既存AWS環境が利用可能 | 設計書4〜6章 |
| 既存Key Pairを参照する | 秘密鍵をTerraformで管理しないため | 具体的なKey Pair名は未決定 | 設計書8章 |
| リージョンを`ap-northeast-1`とする | 既存環境との統一と日本からの利用 | Variableの初期値にする | 設計書6.1 |
| Ubuntu Server 24.04 LTS x86_64を使用する | 既存知識、情報量、互換性を優先するため | AMI取得方法は未決定 | 設計書6.2 |
| インスタンスタイプを`t3.micro`とする | 学習用途に十分でコストを抑えやすい | Variableで変更可能にする | 設計書6.3 |
| インバウンドをSSH 22/TCPだけにする | 必要な通信だけを許可するため | HTTP・HTTPSは対象外 | 設計書7章 |
| SSH接続元を一時的に`0.0.0.0/0`とする | 学習・デモの簡便さを優先するため | 短時間利用し、検証後にdestroyする | 設計書7章 |
| アウトバウンドをすべて許可する | 将来のパッケージ・イメージ取得を考慮するため | フェーズ1の簡略化 | 設計書7章 |
| ローカルStateを使用する | フェーズ1の基本学習に範囲を限定するため | StateはGit管理しない | 設計書13章 |

### 検討した代替案

| 代替案 | メリット | デメリット | 不採用理由・状態 |
| --- | --- | --- | --- |
| VPCからTerraformで構築する | ネットワーク全体をコード管理できる | 初回学習の範囲が広がる | 後続フェーズへ分離 |
| SSH接続元を`/32`へ限定する | 公開範囲を限定できる | 接続元IP変更への対応が必要 | 実務推奨。今回は短時間デモを優先 |
| Session Managerを利用する | SSHポートを公開せず接続できる | IAMなど追加設計が必要 | 将来の拡張候補 |
| ARMインスタンスを使用する | コスト効率を改善できる場合がある | ARM固有差異が学習へ入る | 今回はx86_64を採用 |
| リモートStateを使用する | 共有、ロック、継続運用に向く | バックエンド設計が追加で必要 | 後続フェーズへ分離 |

### 条件が変わった場合の影響

| 条件変更 | 影響する設計 | 対応方針 |
| --- | --- | --- |
| 長時間または継続運用する | SSH接続元、State、監視、コスト | `/32`制限、Session Manager、リモートStateなどを再設計する |
| HTTP・HTTPSを公開する | Security Group、Nginx、DNS、TLS | EC2フェーズと分離したPlan・設計書で扱う |
| 複数環境で利用する | Variables、State、命名、タグ | 環境分離とリモートStateを検討する |
| VPCもTerraform管理する | 管理境界、依存関係、destroy範囲 | ネットワーク専用のPlanと設計書を先に作成する |
